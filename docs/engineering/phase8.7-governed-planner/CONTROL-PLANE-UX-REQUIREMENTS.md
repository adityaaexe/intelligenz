# Control-plane UX requirements — plans, approval, programme execution

**Status: requirements only.** No INTELLIGENZ Figma file key was supplied, so no design file
was created and no AI credits were spent. No UI code is proposed by this document, and no
existing application screen is to be changed as part of Phase 8.7.

`apps/web` has **no** programme or plan surface today (verified: no match for
`programme` under `apps/web/src`). This document defines what such a surface must show and,
more importantly, what it must never imply.

---

## 0. The one rule

> **A proposed plan must never look like an approved programme.**

Every other requirement below is a consequence of that sentence. The failure this rule
prevents is specific: a reviewer sees a clean task list with green ticks, assumes something
was authorised, and stops reading. The system's actual guarantees — that a proposal is
untrusted, that validation is deterministic, that a human decision is required, and that
execution still needs its own approval — are invisible unless the interface makes them
visible.

## 1. Surfaces

### 1.1 Plans list

Org-scoped. Columns: objective (single line, truncated), **status badge**, proposer,
created at, validation (ok / *n* issues), programme reference once submitted.

- Status vocabulary and colour semantics are fixed in §2.
- `invalid` plans are listed, not hidden. A rejected proposal is evidence that the
  validator works.
- No aggregate "plans created" figure is displayed until telemetry is verified — see
  `TELEMETRY-EVENT-CONTRACT.md` §7. A count of rows in this database is not adoption.

### 1.2 Plan review

The decision screen. Required, in this order:

1. **Objective**, verbatim.
2. **Provenance block**: `provider`, `providerModel`, and `simulated`. When `simulated` is
   true the label must read *"Produced by a simulated provider — not a model result."*
   This is not decoration: a plan generated by a stub provider and presented as an AI plan
   would misrepresent the system.
3. **Proposed tasks**, each with `key`, `title`, `goal`, acceptance criteria and
   `dependsOn`. `riskClass` must be labelled **"claimed"**, with a note that the server
   derives the effective class at task creation (`derivedRiskClass`) and that the two may
   differ. Never render the claimed class as the effective one.
4. **Dependency view**: a graph is optional; a table of `task → dependsOn` is mandatory.
   The table is the accessible representation and must be present even if a graph is drawn.
5. **Assumptions** and **unresolved** items, both verbatim and visually prominent. An
   approval of a plan with unresolved items is allowed; the interface must not hide them.
6. **Validation result**: `ok`, or the issue list with `code` and `taskKey`. An `invalid`
   plan shows the issues and **no enabled approve control**.
7. **Decision controls**: approve and reject, each with an optional/required note.

Rules:

- Approve is enabled only when `status === 'proposed'` **and** `validation.ok === true`
  **and** the viewer is `ADMIN` **and** the viewer is not `createdBy`. The last condition
  must be shown as a reason, not a silent disabled button: *"You proposed this plan.
  Another admin must approve it."*
- The approve control must state what it authorises and what it does not:
  *"Approves this proposal. Approved plans still need their tasks approved and submitted."*
- There is no "approve and run" control. Approve and submit are different actions on
  different screens, and the interface must not merge them into one gesture.

### 1.3 Approval state

| State | Display |
|---|---|
| `proposed` | neutral. "Awaiting decision." |
| `invalid` | terminal for approval. Issues shown; approve disabled. |
| `approved` | "Approved by *X* at *T*. Expires *T+TTL*." Submit control available. |
| approved, expired (`approvalExpired: true`) | "Approval expired — the plan must be approved again." Submit disabled. |
| `rejected` | "Rejected by *X* at *T*." Note shown. Terminal. |
| `submitted` | shows the programme reference and links to it. No decision controls. |

The expiry must be visible as an absolute timestamp, and the expired state must not be
shown in the same style as valid approval.

### 1.4 Submit

The submit screen is the only place that says "this will create work". Before the action,
state exactly what will happen: *n* tasks will be created in `ready`, one programme will be
created, and the programme will start. After it, show the programme id and link.

A submit failure must say which step failed and that a retry is safe (every step is
idempotent).

### 1.5 Programme view

- Header: objective, programme status, **`failureCode`** (machine) alongside
  `failureReason` (human).
- Node table: task, node status (`pending running succeeded failed blocked
  waiting_for_approval cancelled`), depends-on, attempts.
- Checkpoint timeline in `sequence` order, each with `outcome` and evidence: `attemptId`,
  `workflowRunId`, `childWorkflowId` (which is `task-<taskId>`), `childRunId`, summary.
- `blocked` programmes must show **why**, from `failureCode`:
  - `APPROVAL_PENDING` → link to the approvals queue, and say that approving the task does
    **not** resume the programme (resumption is a governance decision; see
    `APPROVAL-RESUMPTION-DESIGN.md`).
  - `TASK_FAILED`, `DEPENDENCY_BLOCKED` → name the failed node and the blocked dependents.
  - `DEADLINE_EXCEEDED` → show the deadline.
- Success is shown only for `status === 'succeeded'`. A programme with any node not
  `succeeded` must never present a success indicator, regardless of how many nodes
  completed.

### 1.6 Approvals queue (task-level)

A HIGH/CRITICAL task created from an approved plan appears here as a **PENDING request**.
The queue must state, per item, that plan approval did **not** pre-approve it. This is the
single most likely place for a user to conflate the two decisions.

## 2. Status presentation contract

| Plan status | Label | Tone | Never |
|---|---|---|---|
| `proposed` | "Proposed" | neutral | shown as approved, shown with a success tick |
| `invalid` | "Invalid proposal" | error | offered for approval |
| `approved` | "Approved" | **warning/informational**, not success | shown as running or complete |
| `rejected` | "Rejected" | neutral-negative | editable |
| `submitted` | "Submitted" | informational | shown as succeeded |

| Programme status | Label | Tone |
|---|---|---|
| `pending` | "Submitted" | neutral |
| `running` | "Running" | informational |
| `succeeded` | "Succeeded" | success |
| `failed` | "Failed" | error |
| `blocked` | "Blocked" | warning + reason code |
| `cancelled` | "Cancelled" | neutral-negative |
| `timed_out` | "Timed out" | warning |

Green is reserved for `succeeded`. `approved` is a decision, not an outcome.

## 3. Accessibility

- Status is conveyed by **text plus** colour, never colour alone; every badge carries a
  word.
- The dependency table uses real table semantics (`th`, `scope`), and its caption names the
  plan.
- The approve/reject dialogs trap focus, are dismissible with Escape, and return focus to
  the invoking control.
- Validation issues are associated with their task row via `aria-describedby`, and the
  summary is announced when the review screen loads.
- Any graph rendering is decorative: it must be `aria-hidden` with the table as the
  equivalent, and must not be the only way to see an edge.
- Expiry countdowns must not be the only indicator of expiry; an absolute timestamp is
  required for screen readers and for anyone returning to the page later.

## 4. Forbidden representations

- "AI planned this" as a badge of authority. Provenance is information; it is not approval.
- Any control that approves and submits in one action.
- Any success metric that counts `blocked` or `failed` programmes, or that sums plan counts
  as usage.
- Any label implying that approving a plan approves its HIGH/CRITICAL tasks.
- Any "auto-run" toggle. There is no policy that authorises one, and a disabled control
  for a non-existent feature invites someone to enable it.

## 5. API mapping

| Surface element | Field |
|---|---|
| Plan status | `GET /v1/orgs/:orgId/plans/:planId` → `status` |
| Validation | `validation.ok`, `validation.issues[].code`, `.taskKey`, `.message` |
| Provenance | `provider`, `providerModel`, `simulated` |
| Claimed risk | `tasks[].riskClass` (labelled "claimed") |
| Decision identity | `createdBy`, `approvedBy`, `approvedAt`, `rejectedBy`, `decidedAt` |
| Expiry | `approvalExpiresAt`, `approvalExpired` |
| Programme | `programmeId`, then `ProgrammeResponse` |
| Blocked reason | `ProgrammeResponse.failureCode`, `failureReason` |
| Evidence | programme detail → checkpoints → `evidence` |

- No Figma file, component library change or design-token change.
- No graph visualisation is required; the table is the requirement.
- No mobile layout is specified until the desktop surface exists.
